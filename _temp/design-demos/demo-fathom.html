THE OPERATING PRINCIPLE

每一步都有边界，
每一次变化都可回看。

01

从需求开始，不从配置开始

先说清楚谁在使用、哪些字段重要、怎样流转状态。系统先理解工作，再生成可检查的结构。

A REAL REQUEST / 真实需求

「帮团队管理客户跟进，记录联系人、阶段和下一步；每周提醒负责人。」

02

四步，把意图变成可控系统

从描述到持续运行，所有动作都沿着同一条可追溯的因果链前进。

01 / DESCRIBE

描述工作

补充用户、字段、状态和文件，回答助手追问。

需求有边界
02 / SHAPE

生成结构

服务端 Agent 生成数据结构和界面草稿，供团队检查。

schema 可审
03 / USE

协作处理

登录后搜索、编辑记录，处理表单与业务状态流。

权限先行
04 / OPERATE

授权运行

按定时或事件触发任务，查看运行回执与失败原因。

回执可回看
03

同一句话，长出三个应用变化

它们共享同一条受控链路，却分别落在团队每天真正要处理的工作里。

应用变化 / CRMA / 01

客户跟进

联系人、阶段、下一步被放进同一张工作记录，团队可以从对话转到动作。

01个连续跟进视图
字段 → 状态 → 负责人受控草稿
应用变化 / ORDERSB / 02

订单处理

从待确认到已完成，状态流让每个订单动作都留在团队可见的记录里。

04个关键状态节点
动作 → 状态 → 回执权限门控
应用变化 / OPERATEC / 03

后台任务

把重复的采集、通知和检查交给授权任务，失败时给出可定位的原因。
