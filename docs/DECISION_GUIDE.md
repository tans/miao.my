# MIAO 产品选择指南

如果你需要管理客户、跟进订单、处理内部流程，或定时收集业务信息，MIAO 可以帮助你搭建适合自己团队的工作应用。先看看能做什么，再决定是否部署。

- **看看业务示例** → [/examples.html](/examples.html)
- **开始使用** → [/get-started/](/get-started/)

MIAO 是开源自托管的 AI 工作台：不用先学开发，从一个具体的工作需求出发，搭建应用、让团队使用，再按需要随时调整。本文用事实说明 MIAO 适合什么样的工作、哪些事暂时做不到。结论基于公开源码、文档与已记录的边界；计划中的能力不算当前能力。

## 这些工作，很适合用 MIAO

- **管理业务数据**：把客户、项目、订单整理到自己的应用里，团队在同一处查看和更新。
- **让团队一起用**：邀请同事协作，按成员权限访问数据，谁改了什么都有记录。
- **简化审批和流转**：为具体记录设置状态和操作步骤，例如报价 → 审批 → 成交。
- **自动处理重复任务**：在授权范围内安排定时任务、采集和提醒，例如收集公开招标信息。

## 一分钟，判断是否适合

**适合**：团队需要轻量、可调整的内部业务工具，能接受自行部署与维护。客户管理、订单跟进、内部流程、公开信息采集——这些常见需求 MIAO 都能覆盖。

**需要评估**：需要复杂页面、多系统集成、大规模自动化或对外发布功能时，先用真实流程验证再决定。MIAO 的页面采用受控组件，已发布界面最多 12 个验证页面；不执行用户源码、SQL 或任意代码。

**暂不适合**：希望直接购买托管 SaaS、无需运维，或要求任意脚本、SQL、公开访客写入的团队。MIAO 是自托管产品，服务器、HTTPS、备份与恢复由部署方负责。

## 从一个小应用开始验证

1. **选一个具体问题**，例如客户跟进：把客户、负责人和跟进状态放进一个应用。
2. **搭建并预览**数据表、页面和权限，确认符合你的使用方式。
3. **邀请一位同事试用**，验证发布、记录操作与恢复路径是否符合团队预期。

## 使用前，先了解这些边界

**MIAO 是开源自托管产品，不是托管 SaaS。** 需要由部署者准备服务器、HTTPS、备份与恢复；某些 AI 搭建能力还需要配置相应模型服务及凭据。页面不会承诺“免费模型”“一键生产”“无需运维”或“立即在线试用”。

**页面与动作采用受控组件。** 应用界面由服务端验证的受控组件构成，已发布界面最多 12 个验证页面；不执行用户提交的任意前端源码、SQL 或 shell。附件单文件最多 5 MB（PNG、JPEG、GIF、WebP、PDF、纯文本）；CSV/XLSX 每次读取前 100 行、每批导入最多 100 行，需预览确认。

**公开页面限明确授权的只读信息。** 已发布版本可以选择页面、数据源和字段，提供匿名只读页面；不开放写入、附件、关系或业务动作。公开链接不等于工作区访问授权。

**AI 依赖模型服务。** 对话式搭建、界面草稿等需要模型提案的能力，在未配置 LLM/JEV 模型时不可用；已发布应用的登录、权限、确定性数据操作和已授权的后台任务不依赖模型，配置好即可用。

**模型离线时，什么仍然可用？** 已发布应用的确定性页面、登录与权限检查、已授权的 CRUD、历史运行回执和已有采集结果仍可用；新建或修改应用的 Agent 计划、需要模型理解的摘要与建议会等待服务恢复。

### 六个判断维度（技术细节）

1. **创建方式：Agent-led 还是拖拽/配置优先。** MIAO 定位 agent-first：用户先描述工作，服务端 Agent 通过受限能力生成页面、数据结构和动作候选，再由成员预览和确认。Agent 没有 shell 访问，也不执行用户提交的任意应用源码。如果团队需要可视化画布、表单配置器作为主要创作方式，应与通用低代码平台分别验证。MIAO 不是任意源码、SQL 或 shell 的执行环境。
2. **部署：PocketBase + 单 Go binary 还是多服务/云托管。** MIAO 将 PocketBase 嵌入一个 Go 进程，身份、应用数据和权限由 PocketBase 与 MIAO API 共同处理。数据目录、备份、恢复、域名、HTTPS、邮件和 AI/Jev 密钥由部署方负责。本指南不承诺云托管、SLA、自动扩缩容或免运维服务。
3. **页面范围：受控 JSON UI 与最多 12 个验证页面。** UI schema v3 使用受控的 json-render 组件，页面数据源绑定到真实资源，动作需要声明并经过服务端校验。如果一个应用需要大量自由布局页面、复杂营销站、任意组件或超过 12 页，应先用真实流程验证页面上限是否够用。
4. **发布方式：公开只读与字段授权，还是对外写入门户。** 发布版本可以选择页面、数据源和字段，通过明确的表与字段读取授权提供匿名只读页面。匿名运行时只使用当前已发布版本，不开放写入、附件、关系或业务动作。若需求包含访客提交、文件上传或复杂门户流程，应单独评估认证与写入闭环。
5. **工作闭环：真实记录、状态流、后台任务与采集回执。** MIAO 将真实业务记录保存在 PocketBase，通过 API 检查工作区、应用和记录权限；用户定义的状态机可绑定任意应用表。后台任务可由时间、记录或已认证外部事件触发，并保留运行尝试、权限和幂等回执。需要多系统编排、供应商连接器或大规模自动化时应以实际流程验证。
6. **治理：许可、数据归属、密钥位置与验收证据。** MIAO 源码采用 Apache License 2.0；应用数据和身份以自托管部署的数据目录为中心，部署方负责备份与恢复。长期 AI 凭据保存在服务端。发布、写入和后台运行保留确认或运行回执。本指南不声称任何特定客户、价格、SLA、合规认证或部署结果。

## 建议的验收顺序

1. 用一个真实但边界清楚的内部流程验证“描述 → 草稿 → 预览 → 发布”。
2. 用真实角色验证记录读取、字段权限、状态流和冲突处理。
3. 在隔离环境验证备份、恢复、HTTPS、邮件、AI 密钥和日志策略。
4. 用一个只读公开页面验证页面、字段、图片和撤销发布边界。
5. 再决定是否需要更多页面、外部写入、云托管或更复杂的自动化。
